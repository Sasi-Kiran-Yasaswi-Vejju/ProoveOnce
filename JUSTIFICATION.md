# Why these technologies? (Poseidon, Circom, Groth16, EdDSA, ...)

Every choice below exists to answer one question:
**how can a student prove "CGPA >= 7.5" or "income <= 8 lakh" without revealing the number, cheaply enough to verify on a blockchain?**

---

## 1. Commitment = Poseidon(fields, salt)

**What it is.** A commitment is a fingerprint (hash) of the credential data. It hides the data but locks it in: nobody can later claim different data for the same fingerprint.

**Why Poseidon (and not SHA-256 / Keccak).**
Zero-knowledge proofs work with arithmetic over a big prime field. SHA-256 and Keccak are built from bit operations, which are very expensive to express in that arithmetic (tens of thousands of constraints per hash). Poseidon is designed to be written directly in field arithmetic, so it costs a few hundred constraints. That keeps proof generation fast enough to run in a browser.

**Why a salt.** A CGPA has only a few hundred possible values. Without a random salt, anyone could hash every possible CGPA and match the fingerprint. The random salt makes guessing impossible.

## 2. Circom (+ circomlib)

**What it is.** A language for writing the *rules a proof must satisfy* as arithmetic constraints. Our circuit says: "the hidden fields hash to this commitment, the issuer signed it, and field X compared with threshold T is true."

**Why Circom.** It is the most mature toolchain for this: circomlib already ships audited building blocks we need (Poseidon, EdDSA verification, comparators, bit decomposition), it compiles to a browser-friendly WebAssembly prover, and it has the largest set of tutorials. Alternatives (Noir, Halo2, RISC Zero) are good, but have less ready-made Solidity + browser tooling for a 5-day schedule.

## 3. Groth16 + snarkjs

**What it is.** Groth16 is the proof system (the maths that turns the circuit into a small proof). snarkjs is the JavaScript tool that runs the setup, creates proofs, and generates the Solidity verifier contract automatically.

**Why Groth16.** The proof is only about 200 bytes and on-chain verification costs the least gas of the common systems. Blockchain storage and computation cost money, so tiny proofs matter.

**Trade-off (be honest in your report).** Groth16 needs a one-time "trusted setup" per circuit. Here we run a development ceremony; a real deployment would use a multi-party ceremony. PLONK avoids per-circuit setup but costs more gas.

## 4. EdDSA over BabyJubJub (the issuer's signature)

**What it is.** A digital signature scheme. The university signs the commitment so that anyone can check "this credential really came from the issuer".

**Why this scheme and not Ethereum's ECDSA.** The proof must verify the signature *inside* the circuit (otherwise a student could invent a credential). BabyJubJub is an elliptic curve chosen to live inside the same field the proof system uses, so verifying a signature costs thousands of constraints. Verifying a normal Ethereum (secp256k1 ECDSA) signature inside a circuit would cost millions.

## 5. Solidity smart contracts

| Contract | Purpose |
|---|---|
| IssuerRegistry | Public list of trusted issuers and their signing keys. No central company decides who is trusted. |
| CredentialRegistry | Stores only commitments with expiry and revocation. A cancelled or expired certificate stops working. |
| EligibilityVerifier | Holds each verifier's question, checks the proof, stores only Yes/No. |
| Groth16Verifier | Auto-generated by snarkjs: the maths check of the proof. |

**Why blockchain at all?** (Examiners will ask.)
1. Tamper-proof trust anchor: issuer keys and revocations are public and cannot be quietly changed.
2. No central verification database that can leak or go offline.
3. Anyone can audit that a check happened and what the answer was.
4. The same credential works for any verifier without them contacting the university.

## 6. Hardhat

A local blockchain and test runner. It lets us deploy and test everything in seconds without real money, then deploy the same code to the Sepolia testnet for the demo.

## Security details that make the design more than a toy

| Risk | Defence in this project |
|---|---|
| Student proves an easier question ("CGPA >= 5") | The contract compares the proof's public inputs with the verifier's stored query. |
| Student copies someone else's proof | The proof includes the sender's address; the contract requires it to match msg.sender. |
| Replaying an old proof for a new query | The query id is a public input of the proof (nonce). |
| Fake credential | The circuit verifies the issuer's signature; the contract checks the issuer is registered and the key matches. |
| Wrong authority (university signing an income) | The query can name the required issuer. |
| Old or cancelled certificate | Expiry and revocation are checked on-chain. |
| Guessing hidden values | Random salt in the commitment. |

## Known limitations (state these openly)

- The commitment is public, so two proofs from the same credential can be linked. Fix for future work: a nullifier or Merkle-tree membership proof.
- The setup ceremony here is for development only.
- The system proves "an authorised issuer signed this data", not that the data is true. Trust in the issuer is the root of trust.
- Numbers are limited to 64 bits and 8 fields per credential.
